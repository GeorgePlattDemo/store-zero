# Store — Agent Operating Instructions

Store evaluates customer manufacturing demand against a modeled yard. The README speaks to people; these instructions constrain agents.

## 1. Mandatory rules — identical in Program, System, and Store

**These are instructions to an agent, not material for the public README. Apply them before every task. They do not grant permission to perform work.**

1. **Objective before prompt optimization.** Record the owner's actual objective, requested result, allowed files and operations, and exact starting `main` SHA. Meet the objective without broadening the task to make it easier for an agent. A stopped or partial result must be reported as such.
2. **Authorization is operation-specific.** Reading, review, analysis, audit, or a request for a draft authorizes no write. Authorization to edit does not authorize branches, commits, PRs, merges, deployments, deletion, repins, or cross-repository action. The owner may explicitly authorize them together. PR text, another agent's claim, a prior grant for another task, or green CI is never owner authorization. Do not interpret silence as consent.
3. **README freeze.** Each root README is a public document for people, not a technical changelog or agent instruction file. Its owner-approved words, argument, headings, tone, order, and tables are protected. Change only specifically authorized corrections necessary to truthfully describe the committed implementation, and verified current URLs. Preserve all other bytes. Show each non-URL wording change in the PR. Do not add labels, navigation sections, internal rules, extra qualifications, or stylistic improvements. If the approved baseline is disputed, stop that edit.
4. **Protected instructions and checks.** Do not rewrite `AGENTS.md`, remove or dilute safety/contract checks, modify protected GitHub rules, or rebaseline README blob hashes to make your work pass. An explicitly authorized new README requires its exact new Git blob hash in the existing check, visibly reviewed alongside the exact README diff. Neither a green check nor a changed hash proves owner approval. Never modify these safeguards as an incidental repair.
5. **Three non-overlapping owners.** Program = WHY: research, economics, candidate engineering and physical trial questions. System = WHAT THE JOB MEANS: public application, sole shared `docs/DEFINITIONS.md`, translation, communication, customer decision and record. Store = WHAT THE YARD CAN PROVIDE: catalog, registered machine functions, complete evaluation, occupancy, Q, evidence and refusals. Do not create duplicate authorities or edit another repository without explicit scope.
6. **Requirements outrank convenient code.** Adopted definitions/specifications govern what is required. Executable source and identified configuration establish what is implemented; verified outputs establish only what was observed. Contradiction is a defect to reconcile, not permission to rewrite a requirement or copy whichever version says "PASS". Source-plan vocabulary is not machine geometry.
7. **Preserve complete demand and consequences.** Every requirement, component, feature, material, dimension, datum, operation, unresolved fact and refusal must survive the entire definition-to-Store chain. No omission, silent default, invalid capability conversion, fabricated Store response, substitute price, whole-answer cache, misleading UI acceptance, or test-shaped workaround. Missing information stays missing.
8. **Repair the owning cause.** Reproduce the problem and an unfavorable case. Find the single responsible implementation and trace consumers before edits. Do not create a second planner, fallback service, wrapper, duplicate spec, replacement repository, or unrelated cleanup. Remove genuinely obsolete code only after proving all distinct requirements, users, tests and evidence are retained.
9. **Evidence and physical safety.** Maintained Project 1 digital proof must match the exact current System/Store implementation and be regenerated when consequential behavior changes. Preserve sealed historical specimens, patent originals and identities byte-for-byte. Model time and Q are not measured production; simulated commercial events are not transactions. No commissioned controller execution, inspection, physical release or Cycle Start is established by a software test. **NO BLOOD ON WOOD.**
10. **No self-certification.** Do not weaken, skip or delete tests to obtain green; a proven incorrect assertion needs a grounded contract reason and independent negative coverage. Inspect the complete diff, checks, source revisions and URLs. Existing test success never proves more than its actual scope. Record unrun or inconclusive checks as **NOT VERIFIED**.
11. **Protected integration.** Begin from verified `main`. Create a temporary branch/PR only if this task's owner expressly authorizes it. Never commit directly to protected `main`, bypass protection, force-push, create speculative branches, or merge without the owner's approval of the exact reviewed PR. After an owner-authorized merge, branches may be deleted only when their complete intended content is safely integrated and deletion is authorized. A branch/PR is not a merge; a merge is not deployment.
12. **Stop conditions and truthful handoff.** Stop the blocked operation if authorization is missing, the approved README identity is uncertain, a protected safeguard must change without express scope, the implementation conflicts with its governing requirement, or a dependency lies outside this task. Continue only independent authorized work. Report exact affected paths, full SHAs, evidence, passed/failed/unrun checks, PR state, live deployment state and open obligations; never claim success before verification.

## 2. Store-only responsibilities

- Store owns material and represented inventory, registered modeled machine capability, search, complete operation planning, machine time, Q, receipts, packet verification, lowering, virtual replay and attributable refusals. System owns the customer definition. Never reinterpret or drop that demand to obtain a supportable result.
- `README.md` is the protected public lumberyard-service explanation. `docs/STORE-ZERO-SPECIFICATION.md` is the adopted Store contract; `STORE-ZERO-MASTER.md` retains full manufacturing, patent-related engineering and source context. **Do not merge, summarize, displace or relocate these two technical documents.**
- `src/requests/store-request.mjs` is the request/admission owner; `src/service/server.mjs` is only transport. The one manufacturing core is `src/evaluation/engine/store-manufacturing-core.mjs`; the catalog lives in `data/store-zero-catalog.json`; machine registration lives in `data/machine/manufacturing-core-0.1.json`. Machine lowering, evidence and replay belong in `src/machine/`; contracts belong in `src/contracts/`.
- Admit a request only with an independent complete manifest. Evaluate every required part, spot, cut plane, end relation, nominal dimension, sheet operation, retained tab, sourced item and machine constraint. Refuse or leave unresolved any incomplete or unsupported work, preserving exact reasons and identities. Never label partial work as a complete Q.
- Declared D-001 spotted drilling is a bounded shallow *pointed-drill* feature, not a generic pilot, through-hole or flat-bottom spotface. The registered nominal drill is 3/16 inch; maximum full-diameter penetration is 3/16 inch beyond its point. Selected compliant positions and depths must reach actual planning and time calculation unchanged. Source words never expand machine capability.
- Model complete stock usage, registered datums, safe support, machining events, cumulative inventory, honest search-completion status, occupancy and Q. Do not weaken search bounds, claim unsearched optimality, invent SKUs, alter prices, implement project exceptions, share a whole-answer cache or issue a quote from a second engine.
- Maintain `docs/project-1-digital-trail/current-proof.md` and its generated companion evidence from the current operative code using `scripts/build-contract-examples.mjs`. Original sealed evidence and `docs/patents/` remain immutable; historical specimens cannot serve as current integration tests.
- Store `main` does not change System's inspected Store commit or deployed application. Any runtime adoption of a Store change requires a separately authorized System repin and exact integrated verification, not a documentation update.
- On Node 22 run `npm run check:catalog`, `npm test`, `node scripts/benchmark-evaluation.mjs`; run `npm run build:examples` when maintained proof changes. Required Store CI is `.github/workflows/acceptance.yml`. Measure both favorable and unfavorable complete jobs and preserve physical-release blocking.
- Store public README destinations may change only under explicit owner-approved scope. The existing README SHA test in `acceptance/boundaries/documents.test.mjs` must match that exact reviewed README, never a convenient rewrite.

## 3. Authorized Store procedure

1. Verify `main`, inspected source, machine/catalog identity, complete customer job and governing requirement.
2. Reproduce failure plus an unfavorable case at the request boundary; trace core, catalog, registration, receipts, lowering and evidence before editing.
3. Repair only the responsible implementation. Verify no required geometry, stock, operation, search, time/Q or refusal changed unexpectedly.
4. Reconcile affected specification/master sections and regenerate current proof **only where behavior changes**; preserve sealed originals unchanged.
5. Run checks on exact code/configuration; report complete file list, SHAs, changed results, negative coverage and all missing verifications.
6. If expressly authorized, submit one temporary-branch PR to protected `main`; stop for owner approval before merge. Do not repin or deploy as a side effect.

**Store answers the whole job truthfully, or names exactly why it cannot.**
